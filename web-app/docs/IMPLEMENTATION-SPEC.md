# 안전 전동킥보드 모바일 웹 구현 명세

> 이 문서는 최초 목업과 확정 요구사항을 구현 기준으로 정리한 문서다. 앱 이름과 실제 서비스 데이터는 아직 정해지지 않았으며, 이 문서의 예시 문구는 값이 없는 상태를 전제로 한다.

## 1. 확정 요구사항 요약

### 1.1 변경할 수 없는 요구사항

- React 기반의 반응형 모바일 웹으로 구현한다.
- 스마트폰 세로 화면을 우선하며 데스크톱에서는 최대 너비가 제한된 모바일 앱 화면을 중앙에 표시한다.
- 최초 목업의 흰 배경, 넉넉한 여백, 둥근 카드, 약한 그림자, 선형 아이콘, 큰 제목, 대표 버튼, 고정 하단 내비게이션을 유지한다.
- 색상은 흰색과 블루·블루퍼플 계열을 중심으로 사용한다. 다크 모드, 네온, 초록색 중심 UI, 글래스모피즘은 사용하지 않는다.
- 사용자에게 보이는 문구는 한국어로 작성한다.
- 앱 이름, 로고, 사용자 이름, 위치, 킥보드 정보, 가격, 기록, 센서 수치 등 정해지지 않은 값을 임의로 만들지 않는다.
- 앱 이름은 `APP_NAME` 같은 설정값으로 분리하며, 값이 없으면 이름 영역을 비우거나 “앱 이름”으로 표시한다.
- 헬멧 상태와 발 위치·탑승 상태가 모두 정상이고, 센서가 연결되어 최신 데이터를 전달하며, 오류가 없는 상태가 약 2~3초 안정적으로 유지되어야 안전 확인에 성공한다.
- 안전 확인에 성공하면 짧은 완료 상태를 보여준 뒤 추가 버튼 없이 이용 중 화면으로 자동 이동한다.
- 정상인 항목은 완료 상태를 유지하며 문제가 있는 항목만 실시간으로 다시 확인한다.
- 헬멧 미착용, 데이터 대기, 연결 실패, 오래된 데이터, 센서 오류를 서로 다른 상태로 표현한다.
- 일자형 압력센서의 결과는 세로형 데크, 압력 영역, 발자국 위치로 시각화한다. 원시 압력값을 사용자에게 숫자 목록으로 노출하지 않는다.
- 홈에는 간단한 월간 요약만 두고, 상세 통계는 `내 정보 > 주행 통계`에서 제공한다.
- 이용 중 화면에는 이용 시간, 주행 거리, 요금 항목을 제공하되 실제 데이터가 없으면 값을 꾸며 넣지 않는다.
- 하드웨어 코드는 작성하지 않는다. 앱은 헬멧 Bluetooth 데이터와 데크 Wi-Fi 데이터를 수신·정규화해 상태를 표시하는 역할만 한다.

### 1.2 현재 미정이며 연동 전에 필요한 정보

| 항목 | 필요한 결정 또는 제공 정보 | 값이 없을 때 처리 |
|---|---|---|
| 앱 이름·로고 | 최종 이름, 로고 원본, 사용 규칙 | 이름 없는 임시 심볼과 `APP_NAME` 미설정 상태 유지 |
| 지도 운영 정책 | 현재 Leaflet/OpenStreetMap 타일 기반 위치 지도가 있으며, 배포 규모에 맞는 타일 정책·대체 제공자·필요 시 API 키 확인 | 지도 로딩·권한·오류 카드를 표시하고 가짜 지도를 만들지 않음 |
| 위치·킥보드 API | 위치 권한 정책, 킥보드 목록 API, 식별자와 좌표 형식 | 실제 마커를 만들지 않고 “주변 킥보드 정보가 없어요” 표시 |
| 헬멧 Bluetooth | BLE 여부, Service/Characteristic UUID, 권한 흐름, 패킷 형식 | `unknown`, `connecting`, `sensorUnavailable` 상태 표시 |
| 데크 Wi-Fi | 접속 방식, HTTP/WebSocket 주소, 인증, 메시지 형식 | `unknown`, `connecting`, `sensorUnavailable` 상태 표시 |
| 압력 데이터 | 센서 채널 구성, 보정 방식, 위치 정규화 기준, 상태 판정 주체 | 중립 데크만 표시하고 정상으로 추정하지 않음 |
| 갱신·오래됨 기준 | 전송 주기, heartbeat, stale 판단 임계값 | 설정값으로 분리하고 합의 전에는 임의 임계값을 확정하지 않음 |
| 요금 정책 | 기본 요금, 시간/거리 요율, 반올림, 통화, 서버 계산 여부 | “요금 정보 없음” 또는 “계산 중” 표시 |
| 주행 데이터 | 시작·종료 API, 거리 산정 주체, 시간 기준, 기록 확정 조건 | 이용 중 항목은 `—`, 통계는 빈 상태 표시 |
| 백엔드·DB | API URL, 인증 방식, 데이터 보존 정책, 사용자 식별 방식 | 저장을 성공으로 가장하지 않고 오류/미연동 상태 처리 |
| 로그인·회원가입 | 인증 제공자, 필수 입력, 약관, 계정 정책 | 임의 계정 흐름이나 테스트 사용자를 만들지 않음 |

### 1.3 구현 범위

- 웰컴, 홈, 킥보드 선택, 상세, 안전 확인, 이용 중, 이용내역, 결제, 내 정보, 상세 통계 화면
- 모바일 앱 셸, 상단 바, 카드, 버튼, 하단 내비게이션, 빈 상태·로딩·오류 상태
- 지도 API를 수용하는 지도 컴포넌트와 실제 위치·킥보드 데이터 바인딩 경계
- 헬멧 Bluetooth와 데크 Wi-Fi를 각각 분리한 전송 계층
- 두 센서 스트림을 앱 공통 스냅샷으로 바꾸는 데이터 어댑터
- 안전 확인 상태 머신, 최신성 검사, 안정 유지 구간, 자동 화면 전환
- 이용 시간·거리·요금의 실제 데이터 바인딩 UI
- 주행 기록과 통계 데이터가 존재할 때만 통계·그래프를 표시하는 구조
- 접근성, 반응형 레이아웃, `prefers-reduced-motion` 대응

### 1.4 구현하지 않는 범위

- 아두이노, 펌웨어, 센서 배선, 회로, 핀 설정, 모터 또는 실제 킥보드 구동 코드
- 센서가 보장하지 않는 발 개수·탑승자 수·신뢰도 추정
- 임의의 앱 브랜드, 사용자, 위치, 킥보드, 가격, 기록, 지도 좌표, 센서 수치 생성
- 소셜, 랭킹, 커뮤니티, 게임화, AI 점수·추천·분석
- 관리자용 데스크톱 대시보드
- 제공자·자격 증명·정책이 정해지지 않은 외부 서비스를 연동 완료로 간주하는 것

### 1.5 범위 자체 점검

추가되는 화면과 로직은 확정된 대여 흐름, 안전 확인, 이용 상태, 기록 확인을 완성하기 위한 것에 한정한다. 즐겨찾기, 알림, QR 스캔 등 목업에 보이지만 확정 범위에 없는 기능은 동작 기능으로 확장하지 않는다.

## 2. 사용자 흐름

```text
웰컴
  → 홈
    → 지도/목록에서 실제 킥보드 선택
      → 킥보드 상세
        → 탑승 시작
          → 안전 확인
            ├─ 연결/데이터/착용/발 위치 문제: 같은 화면에서 안내 및 자동 재확인
            └─ 두 조건 정상 + 최신 데이터 + 오류 없음 + 안정 유지
                 → 완료 애니메이션
                   → 이용 중 자동 이동
                     → 실제 이용 종료가 확정되면 기록 저장

홈 월간 요약 → 상세 통계
하단 내 정보 → 주행 통계 → 상세 통계
하단 이용내역 → 실제 기록 목록 또는 빈 상태
하단 결제 → 실제 결제 정보 또는 준비/빈 상태
```

### 2.1 안전 확인 상태 전이

```text
idle
  → connecting
    → checking
      ├─ attentionRequired ── 데이터가 바뀌면 checking
      ├─ error ── 연결이 복구되면 connecting/checking
      └─ 정상 조건 안정 유지 → success → riding
```

- 안정 유지 중 하나라도 조건을 벗어나면 완료 누적을 중단하고 해당 상태를 다시 안내한다.
- 화면 타이머가 끝났다는 이유만으로 `success`로 전환하지 않는다.
- 성공 표시 후 자동 이동하므로 `확인`, `출발` 같은 추가 버튼을 두지 않는다.

## 3. 화면별 상세 설계

### 3.1 웰컴

| 항목 | 설계 |
|---|---|
| 목적 | 서비스의 한 사람 안전 탑승 원칙을 짧게 소개하고 홈으로 진입시킨다. |
| 상단 | 이름 없는 임시 로고 심볼. 앱 이름을 임의로 표시하지 않는다. |
| 중간 | 큰 헤드라인, 짧은 설명, 블루 포인트가 있는 단순 킥보드 일러스트. |
| 하단 | 전체 너비 `시작하기` 버튼과 짧은 안전 문구. |
| 표시 데이터 | 서비스 데이터 없음. |
| 빈 상태 | 로고가 정해지지 않아도 심볼 영역만 유지한다. |
| 로딩 상태 | 필요 없음. |
| 오류 상태 | 필요 없음. |
| 사용자 행동 | `시작하기` 선택. |
| 이동 조건 | 버튼 선택 시 홈으로 이동. |
| 한국어 문구 | “한 사람만, 더 안전하게”, “압력센서와 헬멧 감지로 안전한 탑승을 시작하세요”, “시작하기” |

### 3.2 홈

| 항목 | 설계 |
|---|---|
| 목적 | 실제 주변 킥보드 탐색, 현재 이용 상태, 안전 시스템 상태, 월간 요약을 한눈에 보여준다. |
| 상단 | 중앙 `홈`, 실제 위치 상태 행. 확정되지 않은 지역명은 표시하지 않는다. |
| 중간 | 지도 카드, 주변 킥보드 요약, 이용 상태, 안전 시스템 3열 카드, 월간 요약 카드. |
| 하단 | `홈 / 이용내역 / 결제 / 내 정보` 고정 내비게이션. |
| 표시 데이터 | 위치, 킥보드 목록, 현재 이용, 센서 연결 요약, 월간 주행 횟수·거리·안전 점검 중 최대 2~3개. |
| 빈 상태 | “주변 킥보드 정보가 없어요”, “현재 이용 중인 킥보드가 없어요”, “아직 이번 달 주행 기록이 없어요”. |
| 로딩 상태 | 지도·주변 목록·요약 카드에 텍스트가 포함된 스켈레톤 또는 “불러오는 중”. |
| 오류 상태 | 위치 권한 거부, 지도 설정 누락, 네트워크 오류를 구분해 안내한다. |
| 사용자 행동 | 위치 권한 허용, 지도 마커/주변 목록 선택, 월간 요약의 `자세히 보기`, 하단 탭 선택. |
| 이동 조건 | 실제 킥보드가 선택되면 상세, 요약 선택 시 통계, 하단 탭 선택 시 각 화면. |
| 한국어 문구 | “현재 위치를 확인하고 있어요”, “위치 권한을 허용하면 주변 킥보드를 확인할 수 있어요”, “지도 정보를 불러올 수 없어요”, “기록 없음”, “자세히 보기” |

지도 제공자 키나 좌표가 없을 때 가짜 도로·마커를 그리지 않는다. 지도 제공자가 정해지면 저작권 표기와 이용 약관을 화면에 유지한다.

### 3.3 킥보드 선택

| 항목 | 설계 |
|---|---|
| 목적 | 지도나 주변 목록의 실제 후보 중 한 대를 선택한다. |
| 상단 | 뒤로가기와 `킥보드 선택`. |
| 중간 | 지도 또는 실제 API가 반환한 주변 킥보드 목록. |
| 하단 | 선택된 항목이 있을 때만 상세 진입 행동을 제공한다. |
| 표시 데이터 | 실제 식별 정보, 거리, 이용 가능 상태. 제공되지 않은 필드는 `—`. |
| 빈 상태 | “선택할 수 있는 킥보드가 없어요”. |
| 로딩 상태 | 목록 스켈레톤과 “주변 킥보드를 찾고 있어요”. |
| 오류 상태 | 위치·네트워크·API 오류를 각각 안내한다. |
| 사용자 행동 | 킥보드 항목 선택. |
| 이동 조건 | 유효한 식별자를 가진 실제 항목 선택 시 상세로 이동. |
| 한국어 문구 | “주변 킥보드를 찾고 있어요”, “킥보드 정보를 불러올 수 없어요” |

### 3.4 킥보드 상세

| 항목 | 설계 |
|---|---|
| 목적 | 선택한 킥보드와 요금·주행 가능 정보, 압력센서 안전 시스템을 확인하고 탑승을 시작한다. |
| 상단 | 뒤로가기, 식별 정보 영역. 확정되지 않은 즐겨찾기 기능은 추가하지 않는다. |
| 중간 | 킥보드 일러스트, 배터리·예상 주행거리, 요금, 압력센서 설명. |
| 하단 | `탑승 시작` 대표 버튼. 가격이 실제로 로드된 경우에만 별도 가격을 함께 표시한다. |
| 표시 데이터 | 모델, 식별자, 배터리, 예상 거리, 요금. 모두 nullable이다. |
| 빈 상태 | 각 값은 “정보 없음” 또는 `—`. |
| 로딩 상태 | 카드 단위 스켈레톤과 “불러오는 중”. |
| 오류 상태 | 상세 API 실패 시 오류 안내와 안전한 재요청 행동. |
| 사용자 행동 | 뒤로가기, `탑승 시작`. |
| 이동 조건 | 유효한 킥보드가 있고 탑승 시작 요청을 수락할 수 있을 때 안전 확인으로 이동. 실제 잠금 해제는 앱이 성공으로 가장하지 않는다. |
| 한국어 문구 | “킥보드 정보”, “배터리”, “예상 주행거리”, “이용 요금”, “압력센서 안전 시스템”, “정보 없음”, “탑승 시작” |

### 3.5 실시간 안전 확인

| 항목 | 설계 |
|---|---|
| 목적 | 헬멧과 데크 상태를 동시에 확인하고 사용자가 해결해야 할 행동을 즉시 안내한다. |
| 상단 | 뒤로가기, `안전 확인`, 전체 연결/진행 상태, “출발 전 모든 조건을 확인해 주세요”. |

| 하단 | 안정 유지 진행 상태와 자동 이동 안내. 추가 성공 버튼 없음. |

## 4. 디자인 시스템

### 4.1 색상 토큰

목업에서 추출한 방향을 구현 가능한 근사 토큰으로 정의한다. 최종 시안 검수에서 미세 조정할 수 있다.

```css
:root {
  --color-background: #ffffff;
  --color-surface: #ffffff;
  --color-surface-subtle: #f7f9fc;
  --color-primary: #397bf6;
  --color-primary-strong: #3169ef;
  --color-primary-soft: #eef3ff;
  --color-secondary: #6667e8;
  --color-secondary-soft: #f1f0ff;
  --color-text: #171a22;
  --color-text-secondary: #667085;
  --color-text-tertiary: #98a0ae;
  --color-border: #e7eaf0;
  --color-attention: #ee8a35;
  --color-attention-soft: #fff6ea;
  --color-error: #f04452;
  --color-error-soft: #fff1f2;
  --color-disabled: #dfe2e7;
}
```

색상만으로 상태를 표현하지 않는다. 아이콘, 제목, 설명, `aria-live` 상태 텍스트를 함께 제공한다.

### 4.2 타이포그래피

```css
font-family:
  Pretendard,
  -apple-system,
  BlinkMacSystemFont,
  "Noto Sans KR",
  "Segoe UI",
  sans-serif;
```

| 용도 | 크기 | 굵기 | 행간 |
|---|---:|---:|---:|
| 웰컴 헤드라인 | 32~36px | 800 | 1.25 |
| 페이지 제목 | 19~22px | 700 | 1.35 |
| 섹션 제목 | 17~18px | 700 | 1.4 |
| 카드 제목·핵심 값 | 15~18px | 600~700 | 1.4 |
| 본문 | 14~15px | 400~500 | 1.55 |
| 보조 문구 | 12~13px | 400~500 | 1.5 |

한국어 자간은 약 `-0.02em`으로 통일한다. 실제 값은 화면 폭과 접근성 검수 후 조정한다.

### 4.3 간격·카드·모서리·그림자

- 기본 간격 단위: 4px
- 화면 좌우 여백: 18~20px
- 섹션 간격: 20~24px
- 카드 사이: 10~12px
- 카드 내부: 14~18px
- 카드 반경: 14~16px
- 큰 결과 패널 반경: 18px
- 경계선: `1px solid var(--color-border)`
- 기본 그림자: `0 4px 16px rgba(24, 39, 75, 0.06)`
- 떠 있는 요소 그림자: `0 8px 24px rgba(24, 39, 75, 0.09)`

카드를 중첩하지 않고, 한 카드 안의 하위 영역은 구분선이나 옅은 배경으로 나눈다.

### 4.4 버튼

- 대표 버튼은 최소 높이 56px, 반경 14~16px, 흰색 텍스트, 블루 배경을 사용한다.
- 그라데이션은 대표 버튼에 한해 `#4a96fb`에서 `#376bf4` 정도로 절제해 사용할 수 있다.
- 아이콘 버튼은 최소 44×44px 터치 영역과 `aria-label`을 갖는다.
- 비활성 버튼에는 비활성 이유를 인접 텍스트로 제공한다.
- 안전 확인 성공 뒤에는 버튼을 추가하지 않는다.

### 4.5 아이콘·일러스트

- 둥근 선 끝을 가진 1.8~2px 선형 아이콘을 일관되게 사용한다.
- 아이콘 크기는 일반 행 20~24px, 상태 카드 24~30px, 원형 배경 40~52px를 기준으로 한다.
- 이모지나 플랫폼마다 모양이 다른 문자 아이콘은 사용하지 않는다.
- 킥보드, 헬멧, 데크, 발자국은 사진 대신 목업과 어울리는 단순 SVG/일러스트를 사용한다.
- 로고는 확정 전까지 이름 없는 임시 심볼이다.

### 4.6 하단 내비게이션

- `홈 / 이용내역 / 결제 / 내 정보` 네 항목을 사용한다.
- 높이는 약 72~80px와 `env(safe-area-inset-bottom)`을 함께 고려한다.
- 선택 상태는 블루 아이콘과 굵은 라벨, 비선택은 중립 회색으로 표현한다.
- 본문에 내비게이션 높이만큼 하단 패딩을 확보한다.

### 4.7 상태별 스타일

| 상태 | 색상 | 아이콘·표현 |
|---|---|---|
| 알 수 없음·비활성 | 중립 회색 | 대기 아이콘과 데이터 대기 문구 |
| 연결·확인 중 | 라이트 블루 | 스캔 링 또는 진행 표시와 텍스트 |
| 정상 | 블루·인디고 | 체크 아이콘, 옅은 블루 배경, 완료 문구 |
| 주의 | 소프트 오렌지 | 주의 아이콘, 사용자가 할 행동 안내 |
| 오류 | 코랄·소프트 레드 | 오류 아이콘, 원인과 다음 행동 안내 |

### 4.8 애니메이션

- 헬멧 확인: 부드러운 스캔 회전과 약한 펄스
- 헬멧 완료: 헬멧 위치 정렬, 스캔 링에서 체크로 전환
- 발 위치: 이전 위치에서 새 위치로 보간한 이동과 짧은 페이드
- 압력 영역: 강도·범위 변화에 따른 부드러운 크기/투명도 전환
- 성공: 체크 전환과 짧은 완료 패널 표시 후 자동 이동
- 과도한 흔들림, 폭발, 보상 효과, 반복되는 강한 모션은 사용하지 않는다.
- `prefers-reduced-motion: reduce`에서는 시각 모션을 줄이되 안전 조건의 안정 유지 시간은 생략하지 않는다.

### 4.9 반응형·접근성

- 앱 셸은 `width: 100%`, `max-width: 430px`, `min-height: 100dvh`를 기준으로 한다.
- 휴대폰 프레임, 상태바, Dynamic Island는 웹 UI로 그리지 않는다.
- 넓은 화면에서는 셸을 중앙 정렬하고 약한 외곽선·그림자만 사용한다.
- `env(safe-area-inset-top)`과 `env(safe-area-inset-bottom)`을 반영한다.
- 짧은 화면에서는 콘텐츠가 겹치지 않고 스크롤되도록 한다.
- 입력 화면이 추가될 경우 고정 높이에 의존하지 않고 `scroll-padding-bottom`을 사용해 키보드 가림을 방지한다.
- 상태 변화 영역은 `aria-live="polite"`, 치명적 오류는 상황에 따라 `role="alert"`를 사용한다.
- 포커스 표시, 충분한 대비, 최소 44px 터치 영역을 유지한다.

## 5. 기술 설계

### 5.1 프로젝트 환경과 라이브러리 원칙

현재 프로젝트에서 확인되는 기반은 TypeScript, React, Vite 계열 실행 환경이다. 구현 기준은 다음과 같다.

- TypeScript: 센서 enum, nullable 데이터, 서비스 계약을 컴파일 단계에서 검증하기 위해 사용
- React: 화면과 재사용 컴포넌트 구성
- React Router: 모바일 앱 화면 전환과 동적 식별자 라우팅
- Leaflet: 브라우저 위치를 실제 지도에 표시하는 렌더링 계층. 현재 OpenStreetMap 타일과 attribution을 사용하며 운영 배포 전 제공 정책을 확인
- Lucide React: 목업과 유사한 일관된 선형 아이콘을 최소 의존성으로 제공
- 일반 CSS와 CSS 변수: 목업 기반 디자인 토큰과 애니메이션을 명확히 관리
- 전역 상태 라이브러리를 추가하지 않고 Context + reducer + custom hook으로 시작한다. 복잡도가 실제로 증가할 때만 별도 라이브러리를 검토한다.

설치된 패키지가 있다는 사실과 실제 외부 서비스 연동 완료는 다르다. API 키·URL·권한·데이터가 없으면 연동 상태를 성공으로 표시하지 않는다.

### 5.2 라우팅

| 경로 | 화면 | 진입 조건 |
|---|---|---|
| `/` | 웰컴 | 최초 진입 또는 명시적 이동 |
| `/home` | 홈 | 시작하기 이후 |
| `/scooters` | 킥보드 선택 | 홈의 탐색 행동 |
| `/scooter` | 킥보드 상세 | 실제 식별자가 있는 항목 선택 |
| `/safety-check` | 안전 확인 | 상세에서 탑승 시작 요청 |
| `/riding` | 이용 중 | 안전 확인 성공과 실제 세션 생성 이후 |
| `/history` | 이용내역 | 하단 내비게이션 |
| `/payment` | 결제 | 하단 내비게이션 |
| `/profile` | 내 정보 | 하단 내비게이션 |
| `/statistics` | 상세 통계 | 홈 요약 또는 내 정보 메뉴 |

현재 화면 경로에는 임의의 동적 ID를 만들지 않는다. 실제 킥보드·주행 식별자는 서비스 응답이나 라우트 state로만 전달하고, 값이 없으면 상세·탑승 행동을 비활성화한다.

### 5.3 권장 폴더 역할

```text
app/

  공통 UI

  safety-check/

```

실제 저장 위치가 프레임워크 규칙에 맞춰 달라져도 역할 경계는 유지한다.

### 5.4 상태 관리

- 라우트 단위 서버 데이터: 해당 서비스와 화면 hook에서 로드한다.
- 센서 연결·스냅샷·안전 상태: `SafetyProvider` 또는 동등한 reducer로 관리한다.
- 이용 세션: 실제 `rideId`, `startedAt`, 거리, 요금, 서버 상태를 별도 컨텍스트/hook으로 관리한다.
- UI 컴포넌트는 Bluetooth, WebSocket, HTTP 요청을 직접 수행하지 않는다.
- 로딩, 빈 상태, 오류, 마지막 정상 값은 명시적으로 구분한다.

### 5.5 센서 서비스 경계

```ts
interface SensorService {
  readonly mode: "real" | "test";
  connect(): Promise<void>;
  disconnect(): Promise<void>;
  subscribe(listener: () => void): () => void;
  getSnapshot(): SensorSnapshot;
}
```

권장 처리 흐름:

```text
Helmet Bluetooth Transport ─┐
                             ├─ SensorDataAdapter
Deck Wi-Fi Transport ────────┘
                                  ↓
                         common SensorSnapshot
                                  ↓
                         reducer / custom hooks
                                  ↓
                                UI
```

- 헬멧 전송 계층은 Web Bluetooth를 쓸 경우 BLE GATT 서비스·특성 규격과 사용자 권한이 필요하다.
- 데크 Wi-Fi는 브라우저가 Wi-Fi 센서를 직접 발견하는 방식이 아니라, 기기 또는 중간 서버가 노출한 HTTPS/WebSocket endpoint 계약이 필요하다.
- 두 연결을 하나의 `connected`로 뭉개지 않고 개별 연결 상태를 보존한다.
- 어댑터는 형식 검증, enum 매핑, 누락값 처리, 수신 시각 기록을 담당한다.
- 알 수 없는 enum이나 잘못된 payload를 정상으로 보정하지 않고 오류 상태로 전달한다.

### 5.6 안전 확인 로직

성공 조건은 모두 `true`여야 한다.

1. 헬멧과 데크 연결이 정상이다.
2. 헬멧 상태가 `worn`이다.
3. 발 감지 상태가 `normal`이다.
4. 두 스트림 모두 최신이다.
5. 파싱·센서 오류가 없다.
6. 위 조건이 설정된 안정 유지 구간 동안 연속으로 유지된다.

- 안정 구간은 확정 요구인 약 2~3초 안에서 관리하며 현재 기본값은 `2_500ms`다.
- 최신성 기준은 전송 주기 합의 후 헬멧과 데크의 개별 `*_STALE_AFTER_MS` 환경 설정으로 관리한다. 설정이 없으면 configuration 오류로 실패 폐쇄한다.
- 안전 확인 화면에 들어온 뒤 헬멧과 데크 양쪽에서 각각 새 메시지를 적어도 한 번 더 받아야 연속 최신 데이터로 인정한다.
- 조건이 깨지면 안정 구간 측정을 취소하고 문제 상태로 돌아간다.
- 성공 상태는 현재 기본 `700ms` 동안 보여준 뒤 조건이 계속 정상일 때만 자동 이동한다.
- 안전 성공은 UI의 자동 이동 조건이지만 실제 잠금 해제·모터 제어를 의미하지 않는다. 실제 출발 승인은 백엔드/하드웨어 팀 계약의 응답을 별도로 확인해야 한다.

### 5.7 데이터 어댑터

어댑터의 책임:

- 원본 Bluetooth/Wi-Fi 메시지 스키마 버전 확인
- 원본 필드와 앱 공통 enum 매핑
- pressure region과 foot position 좌표 정규화
- 누락·잘못된 타입·알 수 없는 값 검출
- 앱 수신 시각 기록과 최신성 판단 지원
- 원본 오류 코드를 사용자용 한국어 메시지 키로 매핑

UI는 원본 패킷 필드나 transport를 import하지 않는다. 하드웨어 형식이 바뀌면 transport와 adapter만 교체한다.

### 5.8 Mock과 실제 서비스 교체

- 기본 실행은 확인 전 상태, `null`, 빈 배열을 사용한다.
- 숫자형 센서·지도·통계 데모 데이터는 허락 없이 만들지 않는다.
- 실제 아두이노 연결 전 검증은 enum 상태만 방출하는 `TestScenarioSensorService`와 reducer/hook 단위 테스트로 수행한다.
- 테스트 서비스는 `NEXT_PUBLIC_ENABLE_SENSOR_SCENARIOS=true` 또는 `VITE_ENABLE_SENSOR_SCENARIOS=true`의 명시적 허용과 `?sensor=test` 요청이 함께 있을 때만 앱 런타임에서 선택된다.
- 위의 이중 opt-in 상태에서만 안전 확인 화면에 enum 시나리오 제어 영역과 “테스트 모드 · 실제 센서 데이터가 아니에요” 배지가 표시된다.
- 시각 데모가 필요해 실제처럼 보이는 값을 사용할 때는 사전 허락을 받고 `DEMO_MODE`를 분리하며 화면에 데모임을 표시한다.
- 앱 코드는 `SensorService` 인터페이스에만 의존하고 환경 설정에서 실제 구현을 선택한다.

### 5.9 지도·위치 구조

```text
브라우저 위치 권한 / 위치 서비스
              ↓
       위치 상태 어댑터
              ↓
Leaflet 지도 UI ← 실제 킥보드 API
```

- 타일 URL과 attribution은 지도 설정 경계에서 관리한다. 현재 OpenStreetMap attribution을 제거하지 않는다.
- 키가 필요한 경우 저장소에 하드코딩하지 않는다.
- 실제 좌표가 없으면 기본 도시 좌표를 임의로 선택하지 않는다.
- 권한 거부, 브라우저 미지원, API 실패, 결과 없음 상태를 구분한다.
- 마커는 실제 킥보드 배열에 있는 항목만 만든다.

### 5.10 주행·통계 데이터 구조

```ts
interface RideTelemetry {
  status: "idle" | "starting" | "riding" | "ended" | "error";
  rideId: string | null;
  startedAt: string | null;
  distanceKm: number | null;
  elapsedSeconds: number | null;
  fareAmount: number | null;
  currencyCode: string | null;
  receivedAt: string | null;
  errorCode: string | null;
}

interface RideStatistics {
  rideCount: number | null;
  totalDistanceKm: number | null;
  totalDurationSeconds: number | null;
  averageDurationSeconds: number | null;
  averageSpeedKph: number | null;
  safetyPassCount: number | null;
  helmetConfirmedCount: number | null;
  multipleRiderSuspectedCount: number | null;
  safetyBlockedCount: number | null;
  monthlyTrend: readonly unknown[];
  recentRides: readonly unknown[];
}
```

타입이 `number`라는 사실은 값을 생성해도 된다는 의미가 아니다. API 응답이 없으면 `null` 또는 빈 배열을 유지한다. 통계 계산 기준과 집계 주체는 백엔드 계약으로 확정한다.

### 5.11 오류 처리

- transport 오류, payload 검증 오류, 최신성 오류, 비즈니스 상태를 다른 오류 코드/상태로 유지한다.
- 알 수 없는 오류는 “정보를 확인할 수 없어요”처럼 사실만 말하고 정상으로 추정하지 않는다.
- 마지막 정상 데이터를 유지하더라도 오래된 데이터임을 표시하고 안전 성공 판정에는 사용하지 않는다.
- 외부 API 재시도는 중복 요청과 배터리 소모를 고려한 정책으로 구성하며, 무한 재시도하지 않는다.
- 화면 오류 메시지는 사용자를 탓하지 않고 다음 행동을 알려준다.

### 5.12 반응형 구조

```text
body
└─ mobile app shell (100%, max 430px, min-height 100dvh)
   ├─ top bar / safe-area
   ├─ scrollable main
   └─ sticky or shell-scoped fixed bottom area / safe-area
```

- 절대 좌표로 전체 화면을 배치하지 않는다.
- 지도, 일러스트, 데크는 컨테이너 비율에 맞춰 줄어든다.
- 안전 확인 카드가 짧은 화면에서 잘리지 않도록 본문 스크롤을 허용한다.
- 데스크톱 확장은 대시보드로 바꾸지 않고 모바일 셸을 중앙에 유지한다.
