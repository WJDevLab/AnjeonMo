# 테스트 및 최종 검수 계획

> 원칙: 실제 아두이노가 연결되기 전에는 enum 상태, `null`, 빈 배열, 오류 객체, 테스트 런타임의 가짜 시계만 사용한다. 실제처럼 보이는 센서 수치·지도 좌표·킥보드·사용자·가격·날짜·통계 값은 만들지 않는다.

## 1. 테스트 계층

### 1.1 정적 검증

현재 프로젝트 명령은 `package.json`을 기준으로 실행한다.

```bash
npm install
npm run lint
npm run build
npm test
```

- lint: React hook, TypeScript, 접근성 규칙의 기본 오류 확인
- build: 누락 import, 타입·번들 오류, 클라이언트 전용 API 경계 확인
- test: 현재 등록된 테스트 스크립트 실행

명령이 성공했다는 사실만으로 센서 상태 머신, 지도 외부 API, Bluetooth 권한, Wi-Fi 연결이 검증됐다고 간주하지 않는다. 아래 단위·통합·수동 테스트를 별도로 수행한다.

### 1.2 단위 테스트

- `HelmetDataAdapter`: 허용 enum, 누락값, 알 수 없는 값, 잘못된 형식
- `DeckDataAdapter`: 허용 enum, `null`과 `[]` 구분, 잘못된 배열·위치 객체
- `SensorCoordinator`: 두 연결 종합, 채널별 최신성, 이슈 병합
- 안전 게이트: 모든 조건 AND, 안정 유지, 조건 이탈 시 취소, 자동 성공
- 포맷터: nullable 거리·시간·요금·통계의 한국어 빈 상태
- reducer/hook: 로딩, 빈 상태, 오류, 복구

### 1.3 컴포넌트·라우팅 통합 테스트

- 각 상태에 맞는 한국어 문구와 아이콘이 함께 보이는지 확인
- 성공 상태 뒤 추가 버튼 없이 이용 중 화면으로 이동하는지 확인
- 정상 항목을 유지하고 실패 항목만 안내하는지 확인
- 홈 요약과 내 정보 메뉴가 상세 통계로 이동하는지 확인
- 하단 내비게이션 네 항목의 활성 상태와 이동 확인
- 데이터가 없을 때 가짜 값·마커·그래프가 렌더링되지 않는지 확인

### 1.4 실제 환경 테스트

- 지원 모바일 브라우저에서 Bluetooth 권한과 BLE GATT 연결
- HTTPS 배포 환경에서 데크 WebSocket/HTTP 연결
- 실제 지도 키·도메인·attribution
- 실제 위치 권한 허용·거부·브라우저 미지원
- 실제 백엔드의 주행 시작·종료·통계 계약

외부 자격 증명과 기기 규격이 제공되기 전에는 이 항목을 완료로 표시하지 않는다.

## 2. 숫자형 Mock 없이 테스트하는 방법

### 2.1 상태 테스트 더블

`SensorService`를 구현하는 테스트 더블이 다음 정보만 방출하도록 한다.

- 각 연결 enum
- 헬멧 enum
- 발 감지 enum
- 탑승자 enum
- 전체 스냅샷의 `null`과 빈 배열
- source/category/code만 있는 오류 객체
- 테스트 런타임이 주입한 현재 수신 시각

테스트 더블은 실제 앱의 기본 서비스로 사용하지 않는다. 테스트 환경의 dependency injection에서만 선택한다.

현재 구현의 `TestScenarioSensorService`는 연결·헬멧·발 enum을 바꿀 수 있고 숫자형 센서 데이터를 만들지 않는다. 앱 런타임에서 이 서비스를 선택하려면 테스트 전용 환경 변수 `NEXT_PUBLIC_ENABLE_SENSOR_SCENARIOS=true` 또는 `VITE_ENABLE_SENSOR_SCENARIOS=true`와 URL query `?sensor=test`가 모두 필요하다. 이중 opt-in 시 안전 확인 화면에 “테스트 모드 · 실제 센서 데이터가 아니에요” 배지와 enum 상태 제어 영역이 나타난다. 배포 환경에서는 opt-in 변수를 설정하지 않는다. 자동화 테스트에서는 UI 대신 service 메서드를 직접 호출할 수 있다.

### 2.2 시간 관련 테스트

- 실제 날짜 문자열을 하드코딩하지 않는다.
- fake clock의 “현재 시각”을 adapter/coordinator에 주입한다.
- 최신성 테스트는 fake clock을 설정된 stale 임계값 이후로 이동한다.
- 안정 유지 테스트는 fake timer를 `SAFETY_STABLE_DURATION_MS`까지 진행한다.
- 시계가 움직였어도 안전 조건이 하나라도 비정상이면 성공하지 않아야 한다.

### 2.3 데크 위치 시각화의 제한

발자국의 실제 위치 이동·보간·압력 강도 표현은 숫자형 위치 fixture가 필요하다. 허락받지 않은 비율이나 압력값을 만들지 않기 위해 아두이노 연결 전에는 다음만 검증한다.

- 데이터 없음: 중립 데크만 표시
- `checking`: 확인 중 스타일과 문구
- `normal`: 정상 상태 문구·색상·체크 전환
- `multiplePressureRegions`: 여러 지점 주의 문구·색상
- `multipleRiderSuspected`: 가능성 표현과 탑승 상태 안내
- `positionInvalid`: 발 위치 조정 안내

실제 위치 보간은 다음 중 하나가 준비된 뒤 검증한다.

1. 하드웨어에서 캡처한 승인 데이터
2. 팀이 명시적으로 허용한 숫자형 데모 fixture
3. 실제 통합 환경의 실시간 데이터

데모 fixture를 사용하면 `DEMO_MODE`로 실제 모드와 분리하고 화면에 데모임을 표시한다.

## 3. 아두이노 연결 전 센서 시나리오

### T-SENSOR-01 센서 연결 전

**입력**

- 전체·헬멧·데크 연결: `unknown`
- 헬멧: `unknown`
- 발: `unknown`
- 배열: `null` 또는 계약에 맞는 빈 배열

**기대 결과**

- 전체 안전 상태는 `idle`이다.
- 정상 체크나 출발 가능 문구가 보이지 않는다.
- “센서 연결을 준비하고 있어요” 또는 데이터 대기 문구가 보인다.

### T-SENSOR-02 센서 연결 중

**입력**

- 필요한 채널 중 하나 이상: `connecting`

**기대 결과**

- 전체 상태는 `connecting`이다.
- “센서와 연결하고 있어요”가 보인다.
- 확인 진행 애니메이션은 제공할 수 있지만 성공 누적은 시작하지 않는다.

### T-SENSOR-03 연결 성공

**입력**

- 헬멧·데크 연결: `connected`
- 센서 판정은 아직 `unknown` 또는 `checking`

**기대 결과**

- 연결과 센서 정상 판정을 구분한다.
- 단순히 연결됐다는 이유로 출발 가능 상태가 되지 않는다.
- 전체 상태는 `checking`이다.

### T-SENSOR-04 연결 실패

**입력**

- 헬멧 또는 데크 연결: `error`
- 해당 source의 connection issue

**기대 결과**

- 문제가 발생한 채널을 정확히 표시한다.
- “헬멧 센서와 연결할 수 없어요” 또는 “발판 센서와 연결할 수 없어요”가 보인다.
- 전체 성공과 이용 중 자동 이동이 발생하지 않는다.

### T-SENSOR-05 헬멧 정보 없음

**입력**

- 헬멧 연결은 가능하나 `helmetStatus: unknown`
- `helmetReceivedAt: null`

**기대 결과**

- “헬멧 정보를 기다리고 있어요”가 보인다.
- 미착용으로 단정하지 않는다.
- 헬멧 항목은 완료 상태가 아니다.

### T-SENSOR-06 헬멧 확인 중

**입력**

- `helmetStatus: checking`

**기대 결과**

- “헬멧 착용 상태를 확인하고 있어요”와 짧은 보조 문구가 보인다.
- 스캔·펄스가 과하지 않으며 모션 감소 설정에서는 축소된다.

### T-SENSOR-07 헬멧 미착용

**입력**

- `helmetStatus: notWorn`

**기대 결과**

- “헬멧을 착용해 주세요”가 보인다.
- “착용하면 자동으로 다시 확인해요”가 보인다.
- 재시도 버튼을 강제하지 않는다.
- 발 상태가 정상이라면 발 카드는 완료 상태를 유지한다.

### T-SENSOR-08 헬멧 정상

**입력**

- `helmetStatus: worn`
- 헬멧 메시지는 테스트 clock 기준 최신

**기대 결과**

- “헬멧 착용이 확인됐어요”와 체크 상태가 보인다.
- 발 상태가 아직 정상이 아니면 전체 성공하지 않는다.

### T-SENSOR-09 압력 데이터 없음

**입력**

- `pressureValues: null`
- `detectedPressureRegions: null`
- `estimatedFootPositions: null`
- 발 상태: `unknown`

**기대 결과**

- 데크는 중립 상태로 보이며 발자국·압력 영역을 만들지 않는다.
- “발판 정보를 기다리고 있어요”가 보인다.
- 정상으로 추정하지 않는다.

### T-SENSOR-10 발 위치 확인 중

**입력**

- `footDetectionStatus: checking`

**기대 결과**

- “발 위치를 확인하고 있어요”가 보인다.
- “데크 위에서 잠시 자세를 유지해 주세요”가 보인다.
- 완료 체크는 보이지 않는다.

### T-SENSOR-11 정상적인 발 위치

**입력**

- `footDetectionStatus: normal`
- `riderStatus: singleRider`
- 데크 메시지는 테스트 clock 기준 최신
- 위치 배열은 승인 데이터가 없으면 비워 둔다.

**기대 결과**

- “정상적인 탑승 위치예요”, “발 위치 확인 완료”가 보인다.
- 승인 위치 데이터가 없으면 정상 문구는 테스트할 수 있지만 가짜 발 위치를 그리지 않는다.
- 헬멧이 정상이 아니면 전체 성공하지 않는다.

### T-SENSOR-12 여러 압력 지점

**입력**

- `footDetectionStatus: multiplePressureRegions`
- 실제 개수는 제공하지 않음

**기대 결과**

- “여러 압력 지점이 감지됐어요”가 보인다.
- “한 명만 탑승한 뒤 발 위치를 다시 확인해 주세요”가 보인다.
- “발이 몇 개”라고 단정하지 않는다.
- 오렌지 또는 코랄 주의 스타일과 아이콘을 함께 사용한다.

### T-SENSOR-13 복수 탑승 의심

**입력**

- `footDetectionStatus: multipleRiderSuspected`
- `riderStatus: multipleRiderSuspected`
- `confirmedFootCount: null`

**기대 결과**

- “복수 탑승 가능성이 감지됐어요”가 보인다.
- 확정 인원이나 발 개수를 표시하지 않는다.
- 정상인 헬멧 카드는 완료 상태를 유지한다.

### T-SENSOR-14 위치 이상

**입력**

- `footDetectionStatus: positionInvalid`

**기대 결과**

- “발 위치를 조정해 주세요”와 사용자가 취할 행동이 보인다.
- 발 상태가 다시 `checking` 또는 `normal`로 바뀌면 버튼 없이 자동 재확인한다.

### T-SENSOR-15 데이터 수신 지연

**입력**

- 연결은 유지되지만 새 메시지가 예상 주기에 도착하지 않는 중간 상태

**기대 결과**

- 즉시 미착용이나 센서 오류로 단정하지 않는다.
- “최신 정보를 기다리고 있어요”가 보인다.
- 안정 유지 누적을 일시 중단한다.

### T-SENSOR-16 오래된 데이터

**입력**

- fake clock을 합의된 stale 임계값 이후로 이동

**기대 결과**

- 해당 채널 상태가 `stale`로 파생된다.
- “헬멧 정보가 지연되고 있어요” 또는 “발판 정보가 지연되고 있어요”가 보인다.
- 마지막 상태가 정상이었어도 안전 성공에 사용하지 않는다.
- 최신 메시지가 오면 자동으로 다시 확인한다.

### T-SENSOR-17 잘못된 데이터 형식

**입력**

- JSON이 아니거나 필수 필드 타입·enum이 계약과 다른 payload

**기대 결과**

- adapter가 예외를 UI까지 throw해 화면을 깨뜨리지 않는다.
- malformed issue와 오류 상태를 전달한다.
- 잘못된 값을 기본 정상값으로 바꾸지 않는다.

### T-SENSOR-18 일부만 정상

**입력 A**

- 헬멧 `worn`, 발 `positionInvalid`

**입력 B**

- 헬멧 `notWorn`, 발 `normal`

**기대 결과**

- 각 입력에서 정상 항목은 체크 상태를 유지한다.
- 문제 항목의 행동 안내만 계속 표시한다.
- 전체 성공하지 않는다.

### T-SENSOR-19 전체 안전 확인 완료

**입력**

- 두 transport `connected`
- 헬멧 `worn`
- 발 `normal`
- 탑승자 상태가 허용 상태
- 두 채널이 테스트 clock 기준 최신
- 이슈 없음

**절차**

1. 정상 조건을 방출한다.
2. 안전 확인 진입 뒤 헬멧과 데크 양쪽에서 각각 새 heartbeat 또는 유효 메시지를 방출한다.
3. fake timer를 안정 유지 설정값 직전까지 진행한다.
4. 아직 성공하지 않았는지 확인한다.
5. 정상 조건을 유지한 채 설정값까지 진행한다.

**기대 결과**

- 설정값 전에는 `success`가 아니다.
- 한쪽이라도 화면 진입 이후 새 메시지가 없으면 시간만 지나도 성공하지 않는다.
- 약 2~3초의 안정 유지가 완료된 뒤에만 “모든 안전 확인이 완료됐어요”가 보인다.
- 짧은 완료 표시 후 추가 버튼 없이 이용 중 화면으로 이동한다.

### T-SENSOR-20 안정 유지 중 조건 이탈

**입력**

- 정상 조건으로 안정 유지 시작
- 완료 전에 헬멧 또는 발 상태를 주의 상태로 변경

**기대 결과**

- 기존 안정 유지 측정이 취소된다.
- 문제 안내 상태로 전환한다.
- 다시 정상으로 돌아온 시점부터 새 안정 구간을 측정한다.

## 4. 주행·기록·통계 테스트

### T-RIDE-01 이용 중 데이터 대기

**입력**

- 주행 세션 필드가 `null`인 상태

**기대 결과**

- `이용 시간`, `주행 거리`, `현재 요금` 라벨은 보인다.
- 값은 `—`, `— km`, “요금 정보 없음”처럼 명시적 빈 상태다.
- 앱이 타이머, 거리, 요금을 임의로 시작하지 않는다.

### T-RIDE-02 실제 이용 시간 연결

**입력**

- staging 또는 실제 백엔드가 제공한 `startedAt`/경과 시간

**기대 결과**

- 실제 기준 시각으로 경과 시간이 갱신된다.
- 새로고침 후에는 서버 세션 기준으로 복구한다.
- 테스트용 임의 시작 시각을 서비스 화면에 표시하지 않는다.

### T-RIDE-03 실제 거리 연결

**입력**

- 합의된 권위 소스가 제공한 거리

**기대 결과**

- 해당 값만 `km` 포맷으로 표시한다.
- 수신 전·오류 시 `— km`를 표시하고 마지막 값을 실제 최신값으로 가장하지 않는다.

### T-RIDE-04 실제 요금 연결

**입력**

- 실제 요금 정책 서비스 또는 백엔드 계산 결과와 통화 코드

**기대 결과**

- 실제 결과만 포맷해 표시한다.
- 통화 또는 요금 정책이 없으면 “요금 정보 없음”이다.
- 프론트엔드가 임의 기본 요금·분당 요금을 적용하지 않는다.

### T-RIDE-05 종료 확인

**입력**

- 실제 종료 요청과 서버/기기의 성공·실패 응답

**기대 결과**

- 버튼 선택만으로 성공 처리하지 않는다.
- 성공 응답 뒤에만 완료 기록으로 이동한다.
- 실패 시 이용 중 상태를 보존하고 다음 행동을 안내한다.

### T-DATA-01 이용 기록 없음

**입력**

- 이용 기록 `[]`

**기대 결과**

- “아직 이용 기록이 없어요”가 보인다.
- 임의 날짜·거리·시간·요금 행을 만들지 않는다.

### T-DATA-02 홈 월간 요약 없음

**입력**

- 월간 값 `null`

**기대 결과**

- 카드 하나 안에서 “아직 이번 달 주행 기록이 없어요”가 보인다.
- 2~3개를 넘는 지표나 장식 그래프를 만들지 않는다.
- `자세히 보기`로 상세 통계에 이동할 수 있다.

### T-DATA-03 통계 데이터 없음

**입력**

- 핵심 통계 `null`
- 추이와 최근 기록 `[]`

**기대 결과**

- 각 값은 `기록 없음` 또는 `—`로 표시한다.
- 빈 차트 축·선·막대·날짜를 그리지 않는다.
- “기록이 생기면 주행 추이를 확인할 수 있어요”가 보인다.

### T-DATA-04 실제 통계 데이터 연결

**전제**

- 실제 또는 팀 승인 staging 데이터가 준비됨
- 집계 기간·단위·정책이 백엔드 계약과 일치함

**기대 결과**

- 실제 응답이 있는 지표만 포맷해 표시한다.
- 실제 시계열이 있을 때만 그래프가 렌더링된다.
- 안전 기록과 최근 이용이 원본 응답과 일치한다.
- 일부 필드가 누락되면 그 필드만 빈 상태로 남고 전체 화면이 깨지지 않는다.

## 5. 지도 테스트

### T-MAP-01 타일 제공자 로딩 실패 또는 설정 없음

- 지도 타일 제공자를 사용할 수 없을 때 가짜 지도를 그리지 않는다.
- “지도 설정이 필요해요”처럼 사용자가 이해할 수 있는 상태를 표시한다.

### T-MAP-02 위치 확인 중

- 실제 위치를 받기 전 임의 도시 좌표로 이동하지 않는다.
- “현재 위치를 확인하고 있어요”와 로딩 상태를 표시한다.

### T-MAP-03 위치 권한 거부

- “위치 권한을 허용하면 주변 킥보드를 확인할 수 있어요”를 표시한다.
- 권한 거부를 네트워크 오류로 표현하지 않는다.

### T-MAP-04 실제 위치·킥보드 연결

- 실제 API 응답 좌표에만 마커를 만든다.
- 빈 배열이면 “주변 킥보드 정보가 없어요”를 표시한다.
- 지도 제공자의 attribution이 유지되는지 확인한다.

## 6. 반응형·접근성·모션 검수

### 6.1 레이아웃

- 좁은 스마트폰 세로 화면에서 카드, 버튼, 글자가 겹치거나 잘리지 않는다.
- `100dvh`와 safe-area가 적용되고 모바일 주소창 변화 후에도 하단 영역이 접근 가능하다.
- 짧은 화면에서 안전 확인 내용이 스크롤된다.
- 데스크톱에서 앱 셸이 중앙에 있고 과도하게 넓어지지 않는다.
- 하단 내비게이션이 본문을 가리지 않는다.

### 6.2 접근성

- 모든 아이콘 버튼에 의미 있는 한국어 `aria-label`이 있다.
- 상태 텍스트를 색상 없이 읽어도 의미가 분명하다.
- 상태 변화가 `aria-live` 영역을 통해 전달된다.
- 오류 아이콘에는 텍스트 설명이 함께 있다.
- 키보드 포커스가 보이고 논리적 순서로 이동한다.
- 최소 터치 영역과 텍스트 대비를 충족한다.
- 비활성 버튼의 이유가 화면 텍스트로 제공된다.

### 6.3 모션

- 스캔·펄스·발 위치 이동·완료 전환이 기능 이해를 돕는 범위에서만 동작한다.
- 과도한 흔들림, 폭발, 게임 보상 효과가 없다.
- `prefers-reduced-motion: reduce`에서 장식 모션이 줄어든다.
- 모션 감소 설정에서도 안전 안정 유지 조건은 우회되지 않는다.

## 7. 최종 검수 체크리스트

### 7.1 디자인·문구

- [ ] 최초 목업의 흰 배경, 여백, 둥근 카드, 약한 그림자, 선형 아이콘, 대표 버튼, 하단 내비게이션을 유지했다.
- [ ] 흰색과 블루·블루퍼플 중심이며 초록색 중심 UI, 다크 모드, 네온, 글래스모피즘을 사용하지 않았다.
- [ ] 모든 사용자 UI 문구가 한국어다.
- [ ] 앱 이름과 사용자 이름을 임의로 만들지 않았다.
- [ ] 사진 중심이 아닌 일러스트·아이콘·지도·단순 도형을 사용했다.
- [ ] 모바일 화면에서 겹침·잘림이 없고 데스크톱에서 모바일 셸이 중앙에 있다.

### 7.2 데이터

- [ ] 위치, 킥보드, 배터리, 거리, 가격, 기록, 센서, 날짜·시간, 좌표를 임의로 만들지 않았다.
- [ ] 미정 값은 `null`, 빈 배열, `정보 없음`, `기록 없음`, `불러오는 중`, `—` 중 적절한 상태로 표시한다.
- [ ] 실제 데이터가 없을 때 가짜 지도 마커와 빈 그래프 장식을 만들지 않았다.
- [ ] 원시 압력값을 사용자에게 숫자로 나열하지 않는다.
- [ ] 정확히 보장되지 않은 발 개수나 탑승자 수를 단정하지 않는다.
- [ ] 숫자형 데모가 필요할 경우 사전 허락, `DEMO_MODE` 분리, 데모 표시를 적용한다.

### 7.3 안전 흐름

- [ ] 헬멧과 발 상태가 모두 정상이어야 성공한다.
- [ ] 두 센서 연결, 최신 데이터, 오류 없음이 성공 조건에 포함된다.
- [ ] 정상 상태가 약 2~3초 안정적으로 유지돼야 완료된다.
- [ ] 타이머만 끝났다는 이유로 성공하지 않는다.
- [ ] 성공 후 추가 버튼 없이 이용 중 화면으로 자동 이동한다.
- [ ] 한 항목만 정상일 때 정상 항목은 완료 상태를 유지한다.
- [ ] 실패한 항목은 같은 화면에서 자동으로 다시 확인한다.
- [ ] 헬멧 미착용, 데이터 없음, 연결 실패, stale, 센서 오류를 구분한다.
- [ ] 발 위치, 여러 압력 지점, 복수 탑승 의심, 센서 오류를 구분한다.
- [ ] 압력 영역과 발 위치는 실제 위치 데이터가 있을 때만 데크 위에 표시한다.

### 7.4 화면·통계

- [ ] 웰컴 → 홈 → 선택 → 상세 → 안전 확인 → 이용 중 흐름이 유지된다.
- [ ] 이용 중 화면에 시간·거리·요금 항목이 있고 실제 값 또는 명시적 빈 상태를 표시한다.
- [ ] 홈 월간 요약은 카드 하나, 최대 2~3개 지표로 단순하게 구성됐다.
- [ ] 내 정보의 `주행 통계` 메뉴에서 상세 통계로 이동한다.
- [ ] 통계는 기간 선택 → 핵심 기록 → 추이 → 안전 기록 → 최근 이용 순서다.
- [ ] 실제 시계열 데이터가 있을 때만 그래프를 렌더링한다.
- [ ] 이용내역·결제 미연동 상태에 임의 데이터를 넣지 않았다.

### 7.5 구조·연동

- [ ] UI 컴포넌트가 Web Bluetooth, WebSocket, HTTP를 직접 처리하지 않는다.
- [ ] 헬멧 Bluetooth와 데크 Wi-Fi transport가 분리돼 있다.
- [ ] 원본 데이터가 `SensorDataAdapter`를 거쳐 공통 스냅샷으로 변환된다.
- [ ] 실제 sensor service로 교체해도 UI 수정이 최소화된다.
- [ ] 양쪽 채널의 수신 시각과 stale을 개별 판단한다.
- [ ] 잘못된 payload를 정상값으로 보정하지 않는다.
- [ ] 앱의 안전 성공과 실제 하드웨어 출발 제어를 동일하게 취급하지 않는다.
- [ ] 아두이노, 배선, 회로, 핀, 모터, 펌웨어 코드가 포함되지 않았다.
- [ ] 지도 키, endpoint, 비밀정보를 소스에 하드코딩하지 않았다.
- [ ] 확정 범위를 벗어난 소셜, 랭킹, 커뮤니티, AI 점수·추천 기능을 추가하지 않았다.

## 8. 완료 판정

최종 완료는 다음 증거가 모두 있을 때만 선언한다.

1. lint, build, 등록된 자동 테스트 결과
2. 위 센서 상태 전이 단위·통합 테스트 결과
3. 모바일·데스크톱 주요 화면의 시각 검수 결과
4. 접근성·모션 감소 검수 결과
5. 실제 지도 자격 증명과 위치 API 통합 결과
6. 실제 Bluetooth·Wi-Fi 하드웨어 또는 승인된 캡처 데이터 통합 결과
7. 실제 백엔드의 주행·요금·통계 계약 검증 결과

외부 정보가 아직 없으면 UI와 교체 가능한 서비스 계층까지 완료된 것으로 구분하고, 실제 연동 완료라고 표현하지 않는다.
